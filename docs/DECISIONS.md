# 技术决策记录（DECISIONS）

记录**偏离规格**或规格未明确、但影响后续实现的技术决策。
格式：决策 → 原因 → 替代方案 → 影响。

---

## D-001 用 WSL2 原生 PostgreSQL 代替 docker compose 做本机验证

**日期**：阶段 0
**状态**：已采纳（仅影响"本机验证方式"，不影响交付物）

**背景**：规格要求 dev 环境用 Docker Compose。实测本机 Docker Desktop 无法启动：

```
engine linux/hyperv failed to start: starting Hyper-V VM: 500
系统内存不足，无法启动虚拟机 DockerDesktopVM，需要内存 2048 MB (0x8007000E)
```

宿主机总内存 7.4 GB，空闲 0.8~2.7 GB，且规格要求的 PostgreSQL + Redis + API + Next.js
同时运行远超可用内存。

**决策**：
1. `docker-compose.yml` 仍按规格完整交付（PostgreSQL 16 + Redis 7 + API + Web，
   含 healthcheck、依赖顺序、卷挂载、AUTO_MIGRATE/AUTO_SEED），作为**标准 dev 启动方式**。
2. 本机的数据库层验收改在 **WSL2 Ubuntu 24.04 的原生 PostgreSQL 16.15** 上真实执行，
   连接串与 Docker 完全一致（`postgresql+psycopg://gaokao:...@127.0.0.1:5432/gaokao`）。
3. `docs/KNOWN_LIMITATIONS.md` 明确标注 docker compose 未在本机实测。

**替代方案**：安装 Windows 原生 PostgreSQL —— 放弃，因为 WSL 已在机器上且
Linux 与容器行为更接近，迁移脚本的行为更有代表性。

**影响**：迁移、约束、索引、集成测试的**正确性是被真实验证过的**；
唯一未被本机验证的是 compose 编排本身（YAML 语法与镜像拉取可在具备内存的机器上验证）。

## D-002 枚举用 VARCHAR + CHECK，不用 PostgreSQL 原生 enum

**日期**：阶段 1

**原因**：
- 原生 enum 新增取值需要 `ALTER TYPE ... ADD VALUE`，该语句在 PostgreSQL 中
  无法与其它 DDL 在同一事务执行，迁移回退困难。
- 政策取值（批次、类别、要求类型）在 V1→V2 中必然会增加。

**替代方案**：原生 `CREATE TYPE ... AS ENUM`。

**影响**：取值约束仍由数据库强制（CHECK）+ 应用层 `StrEnum` 双重把关；
代价是字符串存储比 enum 多占几个字节，可忽略。

## D-003 同步 SQLAlchemy，不引入 async

**日期**：阶段 1

**原因**：负载形态是"短事务请求 + 一个 CPU 密集的 CP-SAT 求解"。
CP-SAT 是同步阻塞的 C++ 调用，无法被 async 化；把它塞进事件循环反而需要
`run_in_threadpool` 绕路。同步栈的复杂度显著更低，且 Alembic / 测试夹具更直接。

**替代方案**：asyncpg + AsyncSession + `anyio.to_thread` 包装求解器。

**影响**：并发能力由 Uvicorn 的线程池/FastAPI 的 threadpool 承担。
若未来出现高并发只读流量，可只对 catalog 读路径引入缓存（Redis），而不必改栈。

> `ponytail:` 当前未使用任何缓存。当 catalog 读路径出现可测量的瓶颈时，
> 再加 Redis 缓存（规格允许 Redis 仅用于公共查询类数据）。

## D-004 迁移与 ORM 的一致性由测试强制，而非依赖 autogenerate

**日期**：阶段 1

**原因**：autogenerate 生成的迁移不可读、易与手写约束混淆；
而手写迁移容易与模型漂移。

**决策**：手写分阶段迁移 + `tests/test_migrations.py::test_migrations_match_orm_metadata`
用 Alembic 的 `compare_metadata` 做双向差异断言。

**实际收益**：该测试在阶段 1 抓到 4 个真实漂移（`major_preferences` /
`location_preferences` / `university_preferences` 缺少 `preference_profile_id` 单列索引，
`other_preferences` 索引命名不一致），已修复。

**影响**：新增字段/索引必须同时改模型与迁移，否则测试失败。这是刻意的摩擦。

## D-005 服务端默认值只在 DDL 中声明

**日期**：阶段 1

**原因**：DDL 中保留 `server_default` 使原始 SQL 插入（ETL、人工排查）也能工作；
ORM 侧用 Python 默认值即可，无需重复声明，否则 autogenerate 会产生无意义的差异噪音。

**影响**：ORM 层创建的对象不会读回 server_default，而是在 flush 后由数据库填充；
对 `created_at` / `updated_at` 这类时间戳无影响，因为从不参与业务判断。

## D-006 `app/db/__init__.py` 不导入模型

**日期**：阶段 2

**原因**：模型模块 `import app.db.base`，若包根再导入模型就会形成循环导入
（实测触发 `ImportError: cannot import name 'AdmissionCycle' from partially initialized module`）。

**决策**：全部模型的注册列表放在 `app/db/registry.py::ALL_MODELS`，
Alembic `env.py` 与测试从那里导入。

**替代方案**：延迟导入（函数内 import）—— 更隐晦，放弃。

## D-007 志愿上限等政策数字由服务层校验而非前端

**日期**：阶段 2

**原因**：规格第 8 条要求"任何政策数字从数据库读取，不写死在前端或业务代码"。

**决策**：`PreferenceService.create` 从 `admission_cycles.application_limit` 取值：
- `target_count` 缺省时**直接取用**该值；
- 显式传入且超过上限时返回 `RULE_VIOLATION`，并在 `details` 中带上真实上限与 cycle_id。

**影响**：政策调整（如某年上限变化）只需改数据，前后端都不需要发版。

## D-008 Alembic 配置文件必须是纯 ASCII

**日期**：阶段 1

**原因**：Alembic 用 `configparser.read(..., encoding="locale")` 读取 `alembic.ini`。
在中文 Windows 上 locale 编码是 GBK，文件中的 UTF-8 长破折号会触发
`UnicodeDecodeError: 'gbk' codec can't decode byte 0x94`。

**决策**：`alembic.ini` 保持纯 ASCII（注释中避免 em dash）；中文注释只出现在 Python 迁移文件中。

**影响**：迁移文件的 docstring 可以继续用中文（Python 源码默认 UTF-8）。

## D-009 OpenAPI 使用 FastAPI 默认路径 `/openapi.json`

**日期**：阶段 2

**原因**：部分工具链默认探测 `/openapi.json`。规格只要求"OpenAPI 可访问"，
未指定路径。

**影响**：Swagger UI 仍在 `/docs`，Redoc 在 `/redoc`，业务接口统一在 `/api/v1`。

## D-010 前端 lint 与 build 分离

**日期**：阶段 8

**原因**：Next.js 15.1 内置的 ESLint 运行器仍向 ESLint 传入 `useEslintrc` 与 `extensions`，
而 ESLint 9 已移除这两个选项，同时使用 flat config 时会直接报
`Invalid Options: - Unknown options: useEslintrc, extensions`，导致 `next build` 失败。

**决策**：
1. 前端使用 ESLint 9 flat config（`eslint.config.cjs`，通过 `FlatCompat` 继承
   `next/core-web-vitals` 与 `next/typescript`）。
2. `package.json` 的 `lint` 脚本改为直接调用 `eslint src`（不再用 `next lint`）。
3. `next.config.ts` 设置 `eslint.ignoreDuringBuilds = true`，build 只做编译与类型检查。

**替代方案**：回退到 `.eslintrc.json`（legacy config）——放弃，因为 ESLint 9 的
flat config 是当前标准，且 legacy 模式会在 ESLint 10 被移除。

**影响**：`pnpm build` 不再包含 lint，必须显式运行 `pnpm lint`。README 与本节都写明了这一点；
`next build` 仍然执行 TypeScript 类型检查（输出中的 "Checking validity of types"）。

## D-011 单科成绩接受外语语种，选考科目不接受

**日期**：阶段 9

**原因**：端到端验收时发现 `subject_scores` 拒绝了 `ENG`。英语单科要求很常见
（DEMO 数据里就有一条"英语不低于 115 分"），但外语不是山东 6 选 3 的选考科目。

**决策**：拆成两个 Literal：
- `subjects`（选考科目）仍严格限定 `PHY/CHM/BIO/POL/HIS/GEO`；
- `subject_scores`（单科成绩）额外接受 `ENG/JPN/RUS/GER/FRA/SPA`。

**影响**：单科要求可以被真正校验；选科校验的严格性完全不变。

## D-012 `reset_demo` 默认拒绝删除派生的考生数据

**日期**：阶段 9

**原因**：`seed_demo --reset` 最初直接删快照，触发外键错误
（`sessions` 与 `profiles` 引用它），且如果强行级联会静默删除考生的档案与方案。

**决策**：
1. `reset_demo` 先探测依赖（推荐会话、考生档案），存在依赖时**抛错并说明将删除什么**，
   除非显式传 `force=True`（CLI 为 `--force`）。
2. **不再删除 `admission_cycles`**：它承载政策数字，且重建是幂等的；
   删除它会让合法的考生档案失去引用。同理保留 `reference.*` 字典数据。

**影响**：`--reset` 在干净的数据库上照常工作；在已有考生数据时给出可操作的提示，
而不是抛出一个看不懂的外键错误。

## D-013 ACS 可达上限与风险桶边界不一致（待用户决策，尚未修改）

**日期**：阶段 9（演示数据扩展到全国时发现）

**现象**：把演示数据扩展到 31 个省级行政区后，候选池的风险分布始终没有 SAFE（保）
条目。排查后确认**不是数据问题**，而是公式与桶边界的组合结果。

**原因**：`docs/ALGORITHM.md` 规定 `d_y = clip(ln(q_y/q_c), -0.30, +0.30)`，随后
`ACS = 50 + (BaseACS - 50) * Confidence`。在截断处：

```
HistoryACS = 50 + 35 * tanh(0.30 / 0.07) = 84.99
真实数据下 Confidence 约 0.79  →  ACS = 50 + 34.99 * 0.79 = 77.6
```

而风险桶把 SAFE 定义为 `ACS >= 80`，默认风险组合又要求「稳健模式 20 个 ACS>=80」。
**这三个数字在当前参数下无法同时成立。** 只有把 Confidence 推到 0.95 以上
（需要近乎完美的数据：3 年以上覆盖、官方来源、位次几乎不波动、招生人数充足）
才可能摸到 80。

**决策**：**不擅自修改规格。** 问题、推导过程与三种可选处理方式已写入
`docs/DATA_IMPORT.md` 第六节，并留下验证脚本 `backend/ops/check_acs_ceiling.py`。
演示数据因此把"保"层的实现落在 STABLE 桶（ACS 60~79）。

**影响**：当前三套默认风险组合中的 `ACS>=80` 目标实际不可达，相关硬约束会退化为
不可满足并被钳制。需要用户在以下方案中选择其一，再同步更新 `docs/ALGORITHM.md`
并新增 `model_versions` 记录：① 下调桶边界（SAFE 改为 >=72）；② 放宽 `d_clip`
（0.30 → 0.60）；③ 保持现状，把 `ACS>=80` 明确标注为理论上限。

## D-014 演示数据扩展到全国 31 个省级行政区

**日期**：阶段 9

**原因**：用户反馈"推荐结果只有山东的高校"。排查确认**不是代码缺陷** ——
`RecommendationPipeline._load_plan_rows` 只按 `cycle_id + snapshot_id` 取全部计划，
没有任何省份过滤（`province_code` 参数只被 catalog 查询接口使用）。真正的问题是
演示数据集把 6 所院校全放在了山东，导致地域偏好维度（省份/城市筛选、硬性排除）
无法被演示与验证，也与山东考生实际会填报全国院校的情况不符。

**决策**：

1. 演示院校扩展为 **31 个省级行政区 × 3 个档位（985 / 211双一流 / 普通本科）= 93 所**，
   每所 2 条计划，共 191 条计划、573 条历史录取（另含 5 条手工边界样本）。
2. 院校名称使用**明示的占位名称**（如「演示大学（江苏省·1档）」），代码前缀 `DEMO`。
3. 位次由「参考考生位次百分位 × 档位倍数」反推生成，使五个风险桶都有覆盖。
   初次实现时用的是"先定档位再套公式"，结果 985 在第 30 个省比普通本科还容易 ——
   改为反推后档位倒挂数归零。

**为什么不使用真实院校名称**：为真实院校编造招生计划数与录取位次，会产出一份
看起来权威但实际错误的方案，用户可能据此做出真实的填报决策。规格第 15.2 条也
明确禁止"使用未标注来源的真实招生数字"。真实数据通过 `/api/v1/ingestion/*` 导入。

**影响**：候选池从 17 条扩展到 158 条，省份维度可被真实验证
（`tests/test_location_coverage.py`）。`seed_demo` 耗时仍在 3 秒内。

## D-015 `reset_demo` 保留 cycle 与 source_documents

**日期**：阶段 9

**原因**：`reset_demo` 最初会删除 `admission_cycles` 与 DEMO 的 `source_documents`，
导致两个真实缺陷：

1. 删除 cycle 会触发外键错误（`profiles.cycle_id` 引用它），或更糟 —— 静默级联
   删除考生档案。
2. 删除 `source_documents` 但保留其计划，会让计划指向已删除的来源；再次 seed 时
   由于计划已存在，特殊要求行不会被补回（实测特殊要求数从 4 掉到 2）。

**决策**：

- **保留 cycle**：它承载政策数字，且重建是幂等的；删除它会让合法档案失去引用。
- **保留 source_documents**：条数少，`seed` 对其 checksum 幂等，删除只会破坏溯源。
- **新增孤儿院校清理**：只删除 `ministry_code` 以 `DEMO` 开头**且无剩余计划引用**的院校。
  之前的删除条件要求院校必须有 `program_series`，导致数据集形态变更后残留的
  15 所旧院校永远无法清除。
- **新增依赖探测**：存在考生档案或推荐会话时，`--reset` 会说明将删除什么并拒绝，
  需要显式 `--force`。不静默删除用户数据。

**影响**：`--reset` 在干净库上照常工作；在已有考生数据时给出可操作提示。

## D-016 真实数据只走上传接口，不预置假数据

**日期**：阶段 9

**原因**：用户明确要求"真实数据"。但仓库无法提供真实招生数据，原因是硬性的：

1. 山东省招生计划以《填报志愿指南》形式发布，是分批次逐条列出的大部头出版物，
   没有可编程获取的完整公开来源。
2. 历年投档结果由省考试院分批公布，数据量为数万条。
3. 最关键：即使逐条"查"到数字，也**无法保证准确**。一份看起来权威但有误差的
   录取位次，比没有数据危险得多。

**决策**：交付 `/api/v1/ingestion/*` 上传接口，由用户提供官方 CSV：

- 三个接口分别对应一分一段表、招生计划、投档结果；
- **默认 `dry_run=true`**，先出校验报告再决定是否写库；
- **有一条 error 就整个文件不写入**，不存在"导一半"的状态；
- 列名兼容中英文别名，编码自动识别 UTF-8/GBK，分隔符自动嗅探；
- 每次导入写入 `source_documents`（含 SHA-256、发布单位、来源 URL），
  `quality='OFFICIAL'`、`is_demo=False`；
- 幂等：同内容文件只留一条来源记录，改文件名也认得出来。

完整的字段规格、错误码表、导入顺序与检查清单见 `docs/DATA_IMPORT.md`。

**影响**：演示数据与真实数据走同一套表、同一套列形状，切换时**不需要改动任何
业务代码**，只需导入文件并把 `dataset_snapshots` 换成非 DEMO 的 PUBLISHED 快照。
尚未覆盖的部分（院校基础数据、专业目录、选科要求结构化解析）已在
`docs/DATA_IMPORT.md` 末尾逐项列出，不掩盖缺口。

## D-017 跨年对齐用名称，不用官方代码（实测推翻初判）

**日期**：阶段 10（真实数据接入）

**背景**：拿到真实数据后，看到 `院校代码` 与 `专业代码` 可以 99.6% 精确 JOIN 计划与投档表，
初判应当把 `program_series` 的自然键从名称改为官方代码。

**实测结论：初判是错的。** 用 2022–2025 年 77,460 行普通类一段数据实测：

| 跨年对齐方式 | 2023→2024 | 2024→2025 | 三年连续可对齐 |
|---|---|---|---|
| 官方代码（院校代码+专业代码） | 57.6% | 59.1% | 8,343 |
| 名称（院校基名+专业基名） | 83.5% | 84.3% | **13,790** |

更关键的一点：2024∩2025 代码相同的 12,418 对里，只有 65.4% 的专业基名也相同 ——
**代码会被复用或重编**，把它当身份比名称更不稳定。

**决策**：`program_series.series_key` 继续用 `院校代码|院校基名|专业基名`，
官方代码作为属性保留（写入 `admission_plans.special_requirements` 的「专业代码 X」）。
**不做 schema 迁移。**

**顺带实测**：把专业名里所有括号限定语与「中外合作/校企合作/实验班」等词全部剥离，
对齐率仅从 84.3% 提升到 84.4%，收益可忽略 —— 因此只做最简单的「取第一个括号前」规范化。

**教训**：99.6% 的单年 JOIN 命中率不代表跨年身份稳定。这两个问题不同，
必须分别测量。验证脚本 `scripts/probe_series_identity.py`、`scripts/probe_name_normalisation.py`。

## D-018 一分一段表只用「普通类一段」，deduct 分母为一段达线人数

**日期**：阶段 10

**原因**：一分一段表同时包含「普通类一段」与「普通类二段」，累计到最低分 150 分时
总人数为 681,127。V1 只推荐本科（一段），若把总人数当作位次百分位的分母：

```
考生位次 60,000
  用一段达线人数 333,469  →  q_c = 18.0%   （正确）
  用一段+二段总人数 681,127 →  q_c =  8.8%   （错误，ACS 整体被压低）
```

**决策**：只载入 `批次 == 普通类一段` 的行，`exam_year_stats.ranked_candidates`
取一段部分末行的累计人数。实测各年一段达线人数：

| 年份 | 一段控制线 | 达线人数 |
|---|---|---|
| 2022 | 437 | 301,611 |
| 2023 | 443 | 308,701 |
| 2024 | 444 | 318,935 |
| 2025 | 441 | 333,469 |

**佐证**：2025 年的 333,469 与官方公布「333469 人超本科线」完全一致，
说明解析与口径都正确。

**影响**：回归测试 `tests/test_real_ingestion.py::test_real_dataset_rank_percentile_uses_first_tier_population`

## D-019 优化器必须先裁剪候选池，且超时不能报成不可行

**日期**：阶段 10（真实数据端到端验证时发现）

**现象**：接入真实数据后，`POST /schemes` 返回 400「优化器没有选出任何志愿：
在当前约束下没有可行解（通常是"最低安全数量"高于实际可选数量）」，
但候选池里有 15,202 条合格志愿，`min_safe_count` 也远低于实际可选数。

**根因（两个独立缺陷）**：

1. **把 15,202 个候选全丢给 CP-SAT。** `recommendation_items` 会保存**所有**合格计划
   （真实数据下一万五千条），而 `DEFAULT_POOL_LIMITS` 计算的每桶 120~150 条候选池
   只用于 `stats`，并没有成为求解器的输入。15,202 个布尔变量 + `num_workers=4`
   在 10 秒限时内解不出来，OR-Tools 返回 `UNKNOWN`。

2. **UNKNOWN 被当成 INFEASIBLE 报告。** 代码对「非 OPTIMAL/FEASIBLE」一律返回
   同一句「没有可行解，请降低最低安全数量」——把「求解器没解完」说成「无解」，
   会让用户去调一个根本没有问题的参数。

**决策**：

- 新增 `OptimizerConfig.pool_trim_headroom`（默认 8）。求解前按风险桶裁剪，
  每桶保留 `目标数量 × headroom` 条，桶内按 Preference Score、ACS 降序取；
  用户锁定与 `required_item_ids` 永不裁剪。
  **裁剪放在优化器内部而不是调用方**，这样任何调用路径都受保护。
- 区分 `UNKNOWN`（超时/资源不足）与 `INFEASIBLE` 的提示文案，并在 `diagnostics`
  里回报 `solver_status`、`timed_out`、`candidates_before_trim/after_trim`。

**实测效果**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 求解器输入 | 15,202 条 | 768 条 |
| solver status | UNKNOWN | **OPTIMAL** |
| 选中数量 | 0 | **96** |
| 风险分布 | — | STABLE 31 / SAFE 20 / BORDER 20 / REACH 17 / HIGH_REACH 8（与 BALANCED 目标完全一致） |

**回归测试**：`tests/test_optimizer.py::test_large_pool_is_trimmed_instead_of_timing_out`
（3,000 条候选规模）、`::test_timeout_is_not_reported_as_infeasible`。

**教训**：候选池规模不等于求解器输入规模。`stats` 里算出来的池子如果没真正传给
求解器，限时求解就会静默失败，而错误信息还会把人引向错误的方向。

## D-020 ACS 灵敏度保持现状（λ=0.07 / clip=0.30），用 2025 留出年实测决定

**日期**：阶段 10

**背景**：真实数据下 ACS 直方图在 30–59 区间几乎空白，`REACH`+`BORDER` 两桶合计仅 3.2%，
提出三种候选处理方式（① 放大 λ ② 放宽 d_clip ③ 保持现状并调桶边界），需要选一个。

**先澄清一个前提**：Confidence 与 λ、d_clip、桶边界**无关**。它是
`w_history_coverage·0.25 + w_freshness·0.15 + w_series_match·0.20 +
w_source_quality·0.15 + w_volatility·0.15 + w_plan_quality·0.10`，
六项全部由数据决定。因此「哪个方案的置信度最高」无法用来区分方案 ——
换任何参数，每一条志愿的 Confidence 都是同一个值。

**改用两个能真正区分的判据，并以 2025 年为留出年**（用 2022–2024 算 ACS，
用 2025 实际投档结果检验）：

1. **AUC**：ACS 能否区分「2025 年真的能上」与「真的上不了」的计划。
2. **桶可区分度**：`STABLE` 与 `SAFE` 的真实录取率差值 —— 桶名承诺这两档含义不同。

**实测结果**：

| λ | clip | 非空桶 | STABLE 真实录取率 | SAFE | 差值 |
|---|---|---|---|---|---|
| **0.07** | **0.30** | **5/5** | **99.0%** | **99.8%** | **0.8pp** |
| 0.12 | 0.30 | 5/5 | 99.3% | 99.9% | 0.6pp |
| 0.20 | 0.30 | 4/5 | 99.6% | 空 | — |
| 0.30 | 0.30 | 4/5 | 99.7% | 空 | — |
| 0.25 | 0.80 | 5/5 | 99.5% | 100.0% | 0.5pp |
| 0.40 | 0.80 | 5/5 | 99.7% | 100.0% | 0.3pp |

AUC 各方案都在 0.9886~0.9950，区分能力均已很高，不足以决策。
而**放大 λ 会让桶可区分度下降，且 λ≥0.20 时 SAFE 桶直接消失**；
标准分从 24.6 降到 16.7，说明分数被挤到两端成尖峰。

**校准曲线**（λ=0.07，样本 16,919，考生位次 60,000，整体真实可录取率 70.4%）：

| ACS 区间 | 占比 | 2025 年真实可录取率 |
|---|---|---|
| 0-19 | 6% | 1.0% |
| 20-29 | 22% | 4.6% |
| 30-44 | 3% | 37.8% |
| 45-59 | 1% | 76.7% |
| 60-69 | 5% | 93.4% |
| 70-79 | 53% | 99.6% |
| 80-89 | 10% | 99.8% |

**决策**：**保持 λ=0.07、d_clip=0.30 不变。** 理由：① 桶可区分度最好；
② 唯一能让五个桶全部非空的设置；③ 改参数属于模型变更，需新增 `model_versions`
记录并让已生成的方案失效，在有实测反证的情况下没有理由承担这个代价。

**同时明确一个已知的语义问题**：`STABLE`（60-79）与 `SAFE`（80-100）的真实录取率
只差 0.8 个百分点，两个桶名承诺的「稳」与「保」实际几乎等价。这不是公式缺陷，
而是数据事实 —— 对该考生而言大多数院校专业确实都「基本稳上」，没有任何参数
能把它们分开。真正能让标签诚实的做法是调整桶边界（属产品语义变更），
已记录在此，待产品决策，**未擅自修改**。

**验证脚本**：`scripts/tune_acs.py`（AUC 与分布）、`scripts/calibrate_acs.py`（校准曲线）。

## D-022 体检阈值与计分模型按真实数据重新校准

**日期**：阶段 10

**背景**：体检阈值是在 DEMO 数据上调的。用真实数据跑一份 96 条志愿的方案，
**健康分 0**，警告 38 条、提示 47 条。逐项量化后发现两个独立问题。

### 问题一：阈值切在真实分布的中间，检查失去信息量

用 19,722 条真实计划（2025 年普通类一段）统计：

| 指标 | 真实分布 | 旧阈值 | 旧触发率 |
|---|---|---|---|
| 计划数 | p10=2, **p50=3**, p90=28 | < 5 | **63.1%** |
| 逐年计划变化 | p10=−33%, p50=0%, p90=+50% | 缩减 ≥30% | 15.6% |
| 数据可信度 | min=58.3, p50=72.8 | < 50 | 0.00% |

**山东 63% 的招生计划招生不足 5 人**（中位数只有 3 人），所以「少于 5 人」不是异常，
而是常态 —— 一份 96 条志愿的方案会触发 40 次，等于没有信息。

**决策**：`SMALL_PLAN_THRESHOLD` 5 → **3**（落在真实中位数上，触发率 35.4%）。
`PLAN_REDUCTION_THRESHOLD` 保持 0.30（实测正好是分布的拐点，触发 15.6%）。
`LOW_CONFIDENCE_THRESHOLD` 保持 50.0 —— 复核后确认 `RecommendationItem.confidence`
在 `pipeline.py:450` 被显式 `× 100` 存为 0~100 刻度，与阈值同量纲，实际触发 13.8%，
并非死代码（此前一度误判）。

新增 `PLAN_REDUCTION_MIN_HISTORY = 2`：只有 1 年历史时「中位数」就是那一年，
任何小幅下降都会被读成暴跌，这类样本必须排除。

### 问题二：计分模型按条扣分，单类问题就能把分扣穿

`score_for` 原本是 `100 − Σ 每条 issue 的扣分`。40 条小计划专业 → 扣 200 分 → 触底 0。
**即使把阈值调到最严（小计划 <3、缩减 ≥70%），健康分依然恒为 0**
—— 说明瓶颈不是阈值，而是聚合模型：**position 级检查在多志愿方案上必然刷屏**。

**决策**：按问题**类别**（code）计分：

```
每类扣一次基础分（ERROR 15 / WARNING 5 / INFO 1）
同类多出的条目每条 +1，单类封顶 +3
明细仍逐条列出（什么都不隐藏），只有计分聚合
```

同时把 `PLAN_EXPANDED`（招生计划扩张）加入 `NON_PENALISED_CODES`：
名额增加会拉低录取位次，**对考生有利，不该扣分**。缩减仍然扣分，这个不对称是刻意的。

### 实测效果（同一份 96 条真实方案）

| 指标 | 校准前 | 校准后 |
|---|---|---|
| 健康分 | **0** | **77** |
| 警告 | 38 | 24 |
| 提示 | 47 | 36 |
| `SMALL_PLAN_COUNT` | 40 条 | 17 条（全部落在冲/高冲，不再误报保底位置） |
| 通过 | — | 是（0 个 ERROR） |

### 顺带澄清

早期用 DEMO 数据时曾怀疑 `LOW_CONFIDENCE_THRESHOLD` 与 `SchemeFact.confidence`
量纲不匹配（0~1 vs 0~100）。接入真实数据后复核：**量纲是一致的**，
`ACSEvaluation.confidence` 是 0~1，但写库前统一 `× 100`，体检读的是库里的 0~100 值。
当时的怀疑来自直接读 `ACSEvaluation` 的探测脚本，是探测口径错误，不是产品缺陷。

**验证脚本**：`scripts/calibrate_healthcheck.py`（阈值分布）、
`scripts/sweep_healthcheck.py`（阈值扫描）、`scripts/compare_health_scores.py`（计分模型对比）、
`scripts/audit_healthcheck_codes.py`（issue 代码与严重度审计）。

**回归测试**：`tests/test_healthcheck.py::test_engine_score_groups_by_issue_class`、
`::test_plan_expansion_is_not_penalised`。

## D-025 ETL 的 else 分支漏更新字段（真实缺陷）
