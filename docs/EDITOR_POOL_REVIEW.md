# 志愿编辑器页：候选池与筛选改造方案

> **状态：已实施（阶段 19）。** 候选池改为筛选驱动 + 风险层交错 + 分页，
> 两侧筛选栏均已加上，筛选时禁用拖拽，满 96 条禁用加入。
> 详见 [DECISIONS.md](DECISIONS.md) 的 **D-031**。

**日期**：阶段 19
**当时状态**：只调查与讨论（现已按第六节的决定全部实施）。
**触发**：用户反馈「候选池只有高冲的选项，想做成所有推荐志愿都能选取，并给池子和 96 个志愿池各加筛选」。

---

## 一、根因：为什么候选池只有高冲

不是筛选设置的问题，是**三层原因叠在一起**。

### 第一层：排序键退化成二元值

用户没填「专业/地域/学校」偏好时，`PreferenceService` 里唯一可用的维度是
**「院校层次/升学特征」**，而它只能输出 100 或 0。实测证明：

```
偏好分 100  →  782 条  →  全部是 985
偏好分 66.67 → 2,284 条  →  全部是 211
偏好分 0    → 15,953 条  →  全部是「普通」院校
```

**`preference_score` 实际上就是 `is_985 ? 100 : is_211 ? 66.67 : 0`。**
不是连续偏好度，是院校层次的三档映射。

### 第二层：并列时的 tiebreaker 把最难的排到最前

默认排序是 `偏好分降序 → ACS 升序 → id`。偏好分只有三档，
于是**同一档内部完全由 ACS 升序决定**，也就是「最不安全的最先」。

### 第三层：固定取 500 条，把上面两层的结果放大成"只有高冲"

```
编辑器候选池 limit=500（默认排序）实测：
  HIGH_REACH  500   ← 全部
  REACH         0
  BORDER        0
  STABLE        0
  SAFE          0
  ACS 范围 7.6 ~ 24.0（高冲区间是 0–29）
```

**取到的是全池 19,019 条里 ACS 最低的 500 条 = 最难的 500 个 985 专业。**

### 同一套排序在推荐页也有同样倾向

推荐页默认排序也是 `PREFERENCE`，所以首屏同样是「985 里最难的」。
它没这么刺眼，是因为推荐页有风险层筛选按钮，用户能切走。
**但这意味着：当初为推荐页定「默认保持偏好匹配度」这个决定，是在不知道
`preference_score` 会退化成二元值的前提下做的。**

## 二、实测数据（19,019 条的会话）

### 全池构成

| 风险层 | 条数 | 占比 |
|---|---|---|
| HIGH_REACH 高冲 | 4,931 | 25.9% |
| REACH 冲 | 392 | 2.1% |
| BORDER 边界 | **215** | **1.1%** |
| STABLE 稳 | 7,668 | 40.3% |
| SAFE 保 | 5,813 | 30.6% |

### 方案内 96 条与 BALANCED 目标完全一致

| 风险层 | 实际 | 目标 |
|---|---|---|
| 高冲 | 8 | 8 |
| 冲 | 17 | 17 |
| 边界 | **20** | 20 |
| 稳 | 31 | 31 |
| 保 | 20 | 20 |

**关键矛盾**：方案需要 20 条「边界」，但整个池子只有 215 条边界（1.1%），
而编辑器现在的 500 条窗口里**一条都没有**。
也就是说 —— **用户现在根本无法替换任何一个「边界」志愿。**

### 不同排序下 limit=500 各取到什么

| 排序 | 高冲 | 冲 | 边界 | 稳 | 保 | ACS 范围 |
|---|---|---|---|---|---|---|
| PREFERENCE（当前） | **500** | 0 | 0 | 0 | 0 | 8~24 |
| ACS_DESC | 0 | 0 | 0 | 0 | **500** | 88~94 |
| ACS_ASC | 500 | 0 | 0 | 0 | 0 | 6~14 |
| PLAN_COUNT_DESC | 29 | 2 | 3 | 162 | 304 | 12~94 |
| TUITION_ASC | 122 | 13 | 16 | 205 | 144 | 8~93 |

**结论：任何「单一排序 + 固定 500 条」都会得到某一种单一形态。**
换排序只是换一种偏斜，不是解法。

## 三、现状盘点（两栏各自的能力）

| | 候选池（左） | 我的方案（右） |
|---|---|---|
| 数据来源 | `limit=500` 固定切片 | 方案 96 条全量 |
| 筛选 | **只有**一个文本框，纯客户端 `Array.filter` | **只有**一个文本框，纯客户端 |
| 服务端 `search` | **没用到**（服务端支持却没用） | 不适用 |
| 风险层筛选 | 无 | 无 |
| 分页 | 无 | 无（96 条不需要） |
| 已加入方案的志愿 | 客户端过滤掉（`inScheme`） | — |
| 拖拽排序 | — | 有，但**筛选生效时拖拽语义有问题**（见下） |

### 已确认的两个交互缺陷

1. **满 96 条后「加入」会失败**：实测返回
   `RULE_VIOLATION: 加入后志愿数将超过目标 96 个（当前 96 个），请先删除或调整目标数量`。
   提示是清楚的，但界面上没有预防 —— 用户勾选、点「加入」、才发现失败。
2. **筛选生效时拖拽的语义模糊**：`handleDragEnd` 用**全量** `items` 找索引，
   但界面渲染的是**筛选后**的 `visibleSchemeItems`。
   拖 A 到 B 的位置，实际改变的是全量列表里的位置，中间被隐藏的志愿会一起位移。
   逻辑上说得通（"放到 B 的位置"），但用户看不到发生了什么。

## 四、方案

### 方案 A（根因）：候选池从"固定切片"改为"筛选驱动"

不再请求 `limit=500` 的固定切片，改成和推荐页一样：
**服务端筛选 + 排序 + 分页**。这样"所有推荐志愿都能选取"是通过筛选可达，而不是一次全塞进浏览器。

- 后端 `list_items` 已支持 `risk_bucket / search / province_name / is_985 / is_211 /
  is_double_first_class / sort / limit / offset`（D-030 做的），**大部分能力现成**。
- 需要补一项：**排除已在方案内的志愿**。现在靠前端 `inScheme` 过滤，
  一旦分页就必须由服务端排除，否则 `total` 和页码都会算错。

### 方案 B：候选池筛选栏

| 筛选项 | 为什么需要 |
|---|---|
| **风险层（高冲/冲/边界/稳/保）** | **最关键**。边界只有 215 条（1.1%），任何切片都看不到；而方案需要 20 条 |
| **搜索学校或专业** | 改为服务端全池搜索（现在只搜已加载的 500 条） |
| 省份 | 32 个，想就近或想去某省时必需 |
| 院校层次（985/211/双一流） | 与 preference 退化成二元值直接相关，让用户手动控制 |
| 分页 | 每页 50，与推荐页一致 |

### 方案 C：96 个志愿池的筛选栏

| 筛选项 | 为什么需要 |
|---|---|
| **风险层** | 快速定位「我的 8 个高冲」或「20 个保」，方便逐个替换 |
| **搜索学校或专业** | 想找「我加的那所 XX 大学」在哪一位 |
| 只看未锁定 | 锁定志愿在重新优化时会被保留，编辑时通常想先看可动的 |

### 方案 D：交互修正（顺带）

1. **满 96 条时**：`加入` 按钮直接禁用并提示「已达上限 96，请先删除或调高目标数量」，
   不要等点了才报错。
2. **筛选 + 拖拽**：建议**筛选生效时禁用拖拽**，并提示「筛选状态下不能调整顺序，
   请清除筛选后再拖拽」。理由：拖拽的语义依赖「看得见的相邻关系」，
   而筛选隐藏了中间项，用户无法预测结果。上下移按钮同理，或改为按全量位置移动并明确提示。

## 五、依赖与冲突

1. **A 必须在 B/C 之前。** 筛选控件要落到服务端；否则仍是"过滤已加载的 500 条"，
   筛「边界」还是 0 条。
2. **A 要动 `list_items`，而它在 D-030 刚优化过。** 加排他条件成本很低（新增一个
   `exclude_ids` 或 `scheme_id` 参数），但**必须加索引或确认走现有索引**，
   别把刚修好的 0.4s 又拖慢。
3. **方案变更要让候选池失效。** 加入/删除/重新优化后，池子的"可加入"数量和页码都会变，
   React Query 的 key 必须包含方案版本，否则显示旧计数。
4. **风险层的标签计数。** 现在 `risk_distribution` 是**会话级**的，不含"排除方案内"和
   其它筛选条件。若要标签上显示"可加入的边界还有几条"，需要后端提供**筛选感知的计数**，
   否则标签数字会和列表对不上。这是个必须提前定的细节。
5. **偏好分退化成二元值这件事，会连带影响推荐页的默认排序。** 见待定项 5。

## 六、需要你定的事

1. **候选池的默认视图是什么？**
   - (a) 默认「全部」，按 ACS 降序（稳/保在前）
   - (b) 默认「全部」，但按风险层交错取样，让首页就有五种
   - (c) 默认选中某个风险层（比如「稳」）
   - 我倾向 **(b)**：默认首页就能看到五种形态，用户再按需切标签。
     (a) 会变成"只有保"，把高冲藏起来，和现在的问题镜像。

2. **池子和方案各要哪些筛选项？** 我列的是池子 4 项 + 方案 3 项。
   你说的「各一个筛选功能」如果是指**每栏只要一个控件**，那就得砍到最关键的：
   池子 = 风险层 + 搜索；方案 = 风险层 + 搜索。请确认范围。

3. **筛选生效时拖拽怎么办？**（方案 D2）
   - 禁用拖拽 + 提示（我倾向，最不容易误操作）
   - 允许拖拽，但只在筛选结果内重排（语义复杂，要实现"部分重排"）
   - 允许拖拽，按全量位置移动，并显示"第 X 位 → 第 Y 位"

4. **风险层标签上的数字，要"会话总数"还是"当前可加入数"？**
   前者简单但会与列表对不上；后者准确但要后端加筛选感知的计数。

5. **推荐页的默认排序要不要一起改？**
   实测表明 `preference_score` 在"用户没填偏好"时退化成
   `985/211/普通` 三档。当初你决定"保持偏好匹配度"是在不知道这一点时做的。
   三个选项：维持现状 / 改为 ACS 降序 / 偏好分相同时改用更合理的 tiebreaker
   （现在是 ACS 升序，改成 ACS 降序就能让同档内先看到稳的）。
