# 列表页信息架构问题与改造方案

> **状态：第 1–3 步已实施（阶段 18）。** 修复前 7.7s / 只能看 1.1%，
> 修复后 0.43s / 分页每页 50 条并显示总数，并新增排序控件与折叠式筛选栏。
> 详见 [DECISIONS.md](DECISIONS.md) 的 **D-030**。
> 未实施：方案 C（志愿编辑器页对齐）。

**日期**：阶段 17
**状态**：**只调查与讨论，未改动任何代码。**
**触发**：用户反馈「推荐结果页太乱了，所有结果一股脑全堆在一起」。

## 一、测量结果：问题比"乱"更具体

我先量化，避免凭感觉改。

```
候选池                      19,019 条 / 1,110 所学校 / 32 个省份
推荐结果页实际加载            200 条   = 池子的 1.1%
  其中覆盖的学校              44 所   = 全部学校的 4.0%
  → 1,066 所学校（96%）压根不出现在页面上
志愿编辑器页实际加载          500 条   = 池子的 2.6%
```

**请求耗时（关键）**：

```
limit=50    7.66s     响应 124KB   每条 2,539 字节
limit=200   7.69s     响应 489KB   每条 2,504 字节
limit=500   7.77s     响应 1,216KB 每条 2,491 字节
```

**耗时与 `limit` 几乎完全无关（7.66s / 7.69s / 7.77s）。** 这是根因的直接证据：
时间花在"读全量 + 全量 join"上，不在传输上。

**单条记录的体积也值得注意**：每条返回 **37 个字段**，包含嵌套的
`acs_explanation`、`history`、`plan_count_history`，约 **2.5 KB/条**。
所以 `limit=500` 一次要传 1.2 MB，而**用户每改一次筛选条件都要重付一次**。

200 张卡片 × 每张约 15 个可视元素 ≈ 3000+ DOM 节点，
且这 200 条只来自 34 所学校（最多的一所重复出现 21 次）——
**"一股脑堆在一起"的直接来源就在这里**。

## 二、根因：服务端"先把全量读进内存，再在 Python 里切片"

`app/recommendation/service.py::list_items` 的实现顺序是：

```python
base = select(RecommendationItem).where(...)      # 不带 limit/offset
if risk_bucket: base = base.where(...)
if eligibility: base = base.where(...)
rows = list(self.session.execute(base).scalars())  # ← 19,019 行全部读进来
details = self._plan_details([row.plan_id ...])    # ← 为 19,019 行 join 明细
if search: rows = [ ... Python 里过滤 ... ]         # ← 搜索在内存里做
rows.sort(key=...)                                 # ← 排序在内存里做
page = rows[offset : offset + limit]               # ← 分页在内存里做
```

每一页请求都要付出**全量读取 + 全量 join** 的代价。后果有三个，互相叠加：

1. **慢**：每次翻页 ~9 秒，与页大小无关。
2. **上限被卡死**：前端不敢调大 `limit`（500 已是服务端上限），所以只能显示池子的 1~3%。
3. **前端被迫做"假装"的筛选**：因为拿不到全量，筛选只能在已加载的那一小片上做。

**同一个根因还导致一个功能性缺陷**（下一节）。

## 三、各页面逐项体检

### 3.1 推荐结果页（`/recommendations`）——问题最重

| 现象 | 具体表现 |
|---|---|
| **只能看到 1.1%** | `limit: 200`，池子 19,019 条 |
| **96% 的学校不可见** | 200 条只覆盖 44 所学校，1,110 所里剩下 1,066 所用户根本翻不到 |
| **等待 9 秒** | 与 limit 无关 |
| **一屏堆 200 张卡片** | 每张卡片含 ACS 条、可信度、偏好匹配、计划数、历史位次、学费、按钮，单页正文 3 万+ 字 |
| **筛选只有两档** | 风险层（5 个按钮）+ 搜索框，**仅此而已** |
| **不能排序** | 排序在服务端写死（偏好分降序 → ACS 升序），用户无法改成"按 ACS 降序"或"按学费升序" |
| **没有分页 / 没有无限滚动** | 取回 200 条就结束，用户不知道还有 18,819 条 |
| **搜索可用但体验割裂** | 服务端 search 是有效的（实测「中国石油大学」命中 96 条），但页面在搜索时仍然只显示 200 条窗口内的结果 |

### 3.2 志愿编辑器页（`/schemes`）——同类问题，程度轻一些

| 现象 | 具体表现 |
|---|---|
| **候选池只加载 2.6%** | `limit: 500` |
| **候选池筛选是纯客户端的** | `poolItems` 用 `Array.filter` 过滤已取回的 500 条（`page.tsx:190-198`），**完全没用上服务端已有的 `search` 参数** |
| **同一所学校重复出现** | 因为是"一所学校 × 多个专业"，池子里中国石油大学有 96 条、临沂大学 78 条 —— 缺少"按学校聚合"的视图 |
| 方案内筛选 | 同样是客户端过滤，但方案只有 96 条，**这个没问题** |

### 3.3 体检页（`/health-check`）——基本合理

- 有严重度筛选（必须处理 / 建议处理 / 提示），有问题分组。
- 问题总数 65 条（方案 4），量级可接受。
- **结论：不需要改。**

### 3.4 版本历史页（`/schemes/versions`）

- 只列方案版本，数据量随时间线性增长但很慢。
- **结论：暂不需要改。**

### 3.5 首页 / 成绩页 / 偏好页

- 都是表单，无列表。
- **结论：不需要改。**

## 四、改造方案

### 方案 A（根因，必须先做）：把过滤、排序、分页下推到数据库

**这是所有其他改动的**前提** —— 不修这个，前端加再多筛选控件都还是 9 秒。**

具体：
1. `list_items` 改为在 SQL 里完成：`search` 用 `ILIKE`、排序用 `ORDER BY`、分页用 `LIMIT/OFFSET`。
2. 只对**当前页**的行做 `_plan_details` join（500 行的 join 和 19,019 行的 join 差两个数量级）。
3. `total` 用 `COUNT(*)` 单独查，不再靠 `len(rows)`。

**预期**：每次请求从 ~9s 降到 <0.3s，`limit` 可以放宽到 500 而不疼。

**风险**：`search` 需要 join `admission_plans` + `program_series` + `universities` 才能在 SQL 里过滤学校名/专业名，SQL 会变复杂。这是必要的复杂度。

### 方案 B：推荐结果页的信息架构重做

在 A 的基础上，把"一屏 200 张卡片"改成"先筛选、再看结果"：

**B1. 筛选栏（建议默认折叠，避免又变成一堵墙）**
| 维度 | 数据是否已有 | 说明 |
|---|---|---|
| 风险层 | ✅ 已有 | 保留现有 5 个按钮 |
| 省份 | ✅ 有 `province_name` | 32 个，可多选 |
| 学校层次 | ✅ 有 `is_985/is_211/双一流` | 三个开关 |
| 学费区间 | ✅ 有 `tuition_fee` | 滑块或区间输入 |
| 计划人数下限 | ✅ 有 `plan_count` | 直接回应「1~2 人的专业波动大」这个已知问题 |
| 可信度下限 | ✅ 有 `confidence` | 过滤掉低可信度的 |
| 资格结论 | ✅ 接口已支持 | 现在前端没用 |
| 中外合作 / 民办 | ✅ 有 `cooperative`、`院校性质` | 偏好页已有同类开关 |

**B2. 排序控件** —— 让用户自己选：
- 偏好匹配度（默认，现状）
- ACS 从高到低（想找稳的）
- ACS 从低到高（想冲的）
- 学费从低到高
- 计划人数从多到少

**B3. 分页或无限滚动** —— 明确告诉用户"共 19,019 条，已显示 1–50"。现在连"还有多少"都不显示。

**B4. 卡片瘦身 + 一行摘要**
- 折叠态只显示：学校 · 专业 · ACS · 风险层 · 计划人数
- 展开/弹窗才显示历史位次、学费明细、偏好匹配明细（现在已有「查看解释」弹窗，把更多内容挪进去）

### 方案 C：志愿编辑器页对齐

- 候选池筛选改用服务端 `search`（现在服务端支持、前端没用）。
- 候选池默认只加载一页 + 无限滚动，不再一次性 500 条。
- 增加"按学校聚合"视图（展开某校看它的所有专业），因为池子里同一学校会重复出现 60~96 次。

### 方案 D：体检页与版本页——不动

## 五、依赖与冲突

1. **A 必须在 B/C 之前。** B 的所有筛选控件都依赖服务端能过滤；C 依赖服务端 search。**先做前端会把 9 秒的等待变成 9 秒 × 每个筛选条件。**
2. **A 会影响现有测试。** `list_items` 的排序语义会从"Python 排序"变成"SQL 排序"，浮点排序的边界行为可能有细微差别。E2E 里有断言 `方案条目数 = min(候选数, 上限)` 和风险分布，需要重跑确认。
3. **B2 的排序会与"两步式"原则轻微张力。** 规格里写明「组合优化和最终排序是两步」—— 但那是**优化器**的行为。这里的排序只是**候选池的浏览顺序**，不影响最终方案，所以不冲突。**但要在 UI 上措辞清楚**，避免用户以为改排序就改了方案。
4. **B1 的"计划人数下限"要注意别与体检的 `SMALL_PLAN_THRESHOLD` 重复表达。** 两处都在管小计划，一个用于筛选、一个用于体检扣分，建议在 UI 上统一口径（比如都写"招生人数"）。
5. **B4 折叠卡片会影响现有的浏览器验证脚本**（它按正文文字断言），改动后需要更新断言。

## 六、建议的实施顺序

| 步骤 | 内容 | 前置 | 预计收益 |
|---|---|---|---|
| **1** | 方案 A：过滤/排序/分页下推数据库 | 无 | 9s → <0.3s，是所有后续的前提 |
| **2** | 方案 B3：分页 + "共 N 条"提示 | 1 | 用户知道数据全貌，成本最低 |
| **3** | 方案 B2：排序控件 | 1 | 让用户按自己的目标看 |
| **4** | 方案 B1：筛选栏（先做省份 + 学校层次 + 学费，这三项最常用） | 1 | 从 19,019 收敛到几十条 |
| **5** | 方案 B4：卡片瘦身 | 2 | 降低单屏信息密度 |
| **6** | 方案 C：编辑器页对齐 | 1 | 消除 2.6% 的隐形上限 |

**第 1 步单独就能解决"9 秒"和"只能看 1.1%"这两个最痛的点。**

## 七、需要你定的事

1. **分页还是无限滚动？**（方案 B3）
   - 分页：适合"我要比较第 3 页和第 7 页"的浏览方式，位置感强。
   - 无限滚动：适合"一边刷一边看"，但 19,019 条刷不完，容易迷失。
   - 我倾向**分页**（每页 50），因为志愿填报天然是"逐个比较"，位置感比流畅感重要。

2. **筛选栏默认展开还是折叠？**（方案 B1）
   - 展开：一眼看到能筛什么，但顶部占一大块。
   - 折叠：页面干净，但用户可能不知道能筛。
   - 我倾向**折叠 + 显示已选条件数量**（如"筛选 (2)"）。

3. **默认排序保持"偏好匹配度"吗？**（方案 B2）
   - 保持：与"两步式"设计一致（先按偏好选，再按风险排）。
   - 改成 ACS 降序：更像"我现在只想找稳的"。
   - 我倾向**保持偏好匹配度**，但把排序控件做得显眼。

4. **要不要保留"一屏 200 张卡片"作为一个选项？** 有些人就是喜欢一次看完。我倾向**不保留**，改为每页 50。

5. **优先做哪几步？** 我的建议是 **1 → 2 → 3**（根因 + 分页 + 排序），先解决"慢"和"看不到"，再做筛选栏。也可以 1 → 4 直接上筛选。
